# Phase 2, Module 2: Cart & Checkout (online channel)

**Status:** backend complete and verified end to end against real PostgreSQL, MongoDB and Redis. Stripe's network calls were replaced by a recording fake in the module's own tests; the real Stripe API was verified afterwards (see `Stripe_Setup_And_Verification.md`).
**Builds on:** Commerce Core Foundation (`Phase2_Commerce_Core_Foundation.md`). Online checkout is a thin layer over the shared `createOrder`, pricing and inventory services, so the POS phase reuses the same core.

**Skill search:** `find-skill` was run first. Three candidates were reviewed (Stripe's official `stripe-best-practices`, Hookdeck's `stripe-webhooks`, Redis's `redis-core`). Only `stripe/ai` `stripe-best-practices` was installed, after a full read of `SKILL.md` and its references found nothing suspicious. Its rules shaped this module: fulfil on both `completed` and `async_payment_succeeded` gated on `payment_status`, verify signatures before anything else, use a client instance rather than a global key, and never pass `payment_method_types`.

## Design

**Cart (Redis).** One hash per store and shopper, `cart:{storeId}:{u|g}:{id}`, field = productId, value = quantity, with a 7-day TTL refreshed on every write. Only ids and quantities are stored; title, image, price and stock are looked up fresh on every read, so a cart can never hold a stale or tampered price. The owner is the logged-in user (bearer token) or a guest (`X-Guest-Session-Id`, generated by the frontend). A token that is present but invalid is rejected with 401 rather than silently treated as a guest.

**Checkout session.** `POST /stores/:storeId/checkout/session` prices the cart from the live catalog and the store's tax rate, then **freezes the result as a `CheckoutSession` row** (lines, totals, shipping, currency) before calling Stripe. Stripe receives the line items, a "Tax" line and the shipping rate, which add up exactly to the priced total. Stripe metadata carries only our own ids.

**Webhook.** `POST /webhooks/stripe` is mounted before `express.json()` with a raw body, because the signature is computed over the exact bytes. Order of work: verify the signature, then handle the event.
- `checkout.session.completed` and `async_payment_succeeded` fulfil the order only when `payment_status` is not `unpaid`.
- The order is written from the **snapshot**, not today's catalog. In the test, the product price was changed to 99 after checkout and the order still shows 20, matching what was charged.
- The charged amount and currency must equal the snapshot, otherwise nothing is written and the record is marked FAILED.
- `async_payment_failed` and `expired` close the record.

**Idempotency.** Stripe can deliver the same event twice, even at the same moment. Only a `PENDING` record can be claimed; the claim, the customer, the order, the payment and the stock deduction are one transaction; and `Order.stripeCheckoutSessionId` is unique as a second guard. Verified with two simultaneous deliveries: exactly one order, stock deducted once.

**Out of stock after payment.** Another sale can take the last unit between checkout and payment. The transaction rolls back (no order, no stock change) and the payment is refunded automatically through Stripe with an idempotency key, then the record is marked REFUNDED. If the refund call fails, the webhook answers 500 so Stripe retries, and the key makes the retry safe.

**Customers.** A logged-in shopper is linked to a tenant-scoped `Customer` through their user id; a guest is matched by the email Stripe collected. Each business sees only its own customers.

## Endpoints

| Endpoint | Purpose |
|---|---|
| `GET /stores/:storeId/cart` | Current cart with live prices and availability |
| `POST /stores/:storeId/cart/items` | Add to the quantity; 409 if it would exceed stock |
| `PATCH /stores/:storeId/cart/items/:itemId` | Set an exact quantity (`itemId` is the product id) |
| `DELETE /stores/:storeId/cart/items/:itemId` | Remove an item |
| `POST /stores/:storeId/checkout/session` | Freeze the priced cart, return the Stripe checkout URL |
| `POST /webhooks/stripe` | Signature-verified, idempotent order creation |

Schema addition: `CheckoutSession` (migration `20260919010000_checkout_sessions`, RLS in `manual-sql/003_enable_rls_checkout_sessions.sql`). New dependencies: `ioredis` and `stripe`, both required by the approved plan.

## Verification (49 checks, all passing)

`npx tsx scripts/verify-checkout.ts` drives the real HTTP API. It covers: guest and logged-in cart ownership, adding, capping at stock, TTL, prices never stored in Redis, a price change showing immediately, cross-tenant isolation; checkout totals sent to Stripe; missing and wrong signatures; fulfilment from the snapshot; replay and simultaneous double delivery; unpaid then async success; amount mismatch; unknown events; expiry; the automatic refund when stock runs out mid-payment and no second refund on retry; a logged-in shopper linked to their customer record. A separate check confirmed checkout and the webhook answer a clean 503, and leave no record behind, when Stripe keys are absent. The earlier 21-check foundation suite was re-run and still passes.

One real bug was found by these checks and fixed: `expired` and `failed` events ran their database update after the tenant context had closed (a Prisma query is lazy and was returned instead of awaited inside the callback), which would have made every expired-session event a 500.

## Decisions and known limits

- Tax is added as its own Stripe line item because ZYRO computes tax itself (a flat store rate). Stripe Tax (`automatic_tax`) is not used; enabling it would need a tax registration and would replace this.
- Discount codes are accepted by the schema and refused with 400 until Phase 3, rather than silently ignored.
- Shipping zones are read if `shippingZoneId` is sent, but there is no endpoint to create them until Module 5, so they were created directly in the database for testing.
- Guest cart merge on login is not built; a shopper who logs in after adding items as a guest starts with their user cart.
- Success and cancel URLs point at `${CORS_ORIGIN}/checkout/success?store=...&session_id=...` and `/cart?store=...`. The frontend module will define the real routes and these two URLs will be aligned then.
- Stock is checked at cart, at checkout start and again at payment time, but not reserved; the automatic refund covers the gap.
